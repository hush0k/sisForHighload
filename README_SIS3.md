# SIS #3. Database tuning

## 1. Цель

В SIS #1 был спроектирован сервис счётчиков лайков и просмотров с такой нагрузкой:

- 50M постов, в среднем около 20 лайков на пост;
- запись: около 18k RPS просмотров (после дедупликации) и около 2k RPS лайков/unlike;
- чтение: около 44k RPS (батч для ленты, на каждый пост отдаются likes, views, liked_by_me);
- один пользователь считается один раз на пост за час, просмотр засчитывается при `view_finished - view_started >= 2 с`;
- лайки точные, просмотры с ошибкой < 1%, eventual consistency <= 2 с, read p99 < 50 ms.

В SIS #2 сервис был в памяти. Здесь он переведён на PostgreSQL 18, и по стадиям измеряется, что даёт каждая настройка БД. Результат — таблица p95/p99 до и после каждой стадии и объяснение каждого выигрыша.

Стадии:

| Стадия | Что меняется |
|---|---|
| 0 | baseline: соединение открывается на каждый запрос, `likes` без индексов, лайки считаются `COUNT(*)` |
| 1 | пул соединений HikariCP |
| 2 | первичный ключ `likes (post_id, user_id)` и `INSERT ... ON CONFLICT DO NOTHING` |
| 3 | счётчик лайков читается из `post_counters`, а не считается по `likes` |
| 4 | `likes` партиционирована по hash(post_id), 8 партиций |
| 5 | чтение идёт с read replica |

## 2. Стек и что намеренно не используется

Используется: PostgreSQL 18, Spring Data JPA (Hibernate), Flyway, HikariCP, Docker и Docker Compose, k6, Makefile.

Не используется: Redis, Kafka, шардинг, PgBouncer, JdbcTemplate и чистый JDBC в коде сервиса, Kubernetes, любые кэши, Testcontainers, JUnit-тесты, JMeter, Gatling.

Почему: задача этого SIS — показать, что даёт сама база. Любой кэш или очередь скрыл бы эффект индексов, пула и партиций. Redis, Kafka и агрегатор относятся к SIS #4.

Данные читаются и пишутся только через репозитории Spring Data JPA. Горячие запросы написаны как `@Query(nativeQuery = true)`, чтобы тот же SQL можно было выполнить в `EXPLAIN ANALYZE`. Счётчики обновляются одним `UPDATE`, без load и `save()`.

## 3. Схема и ключевые запросы

Схема создаётся миграциями Flyway. Стадия задаёт, до какой версии миграции применяются.

| Версия | Что делает |
|---|---|
| V1 | `likes` без индексов, `post_counters` (PK `post_id`), `view_dedup` (PK `post_id, user_id`) |
| V2 | `ALTER TABLE likes ADD PRIMARY KEY (post_id, user_id)` |
| V3 | `likes` пересоздаётся как `PARTITION BY HASH (post_id)`, партиции `likes_p0..likes_p7` |

Стадии 0-1 используют V1, стадии 2-3 используют V2, стадии 4-5 используют V3. Откатываться назад нельзя: если база уже новее стадии, приложение откажется стартовать и попросит `make reset`.

Ключевые запросы:

- лайк: вставка в `likes`, при успехе `UPDATE`-upsert в `post_counters`;
- unlike: `DELETE` из `likes`, при успехе `UPDATE post_counters SET likes_count = likes_count - 1`;
- просмотр: `INSERT ... ON CONFLICT (post_id, user_id) DO UPDATE ... WHERE counted_at < :threshold` в `view_dedup`, при успехе upsert `views_count` в `post_counters`;
- чтение ленты: `post_counters WHERE post_id = ANY(:ids)`, количество лайков (до стадии 3 — `COUNT(*) ... GROUP BY post_id` по `likes`), `liked_by_me` — `likes WHERE user_id = :u AND post_id = ANY(:ids)`.

### Почему в baseline у `likes` нет индексов

Baseline должен показывать «как выглядит наивная схема». Без индексов любой `COUNT` по посту и любая проверка `NOT EXISTS` — это seq scan всей таблицы, и именно с ним потом сравнивается каждый шаг. По той же причине baseline вставляет лайк через `WHERE NOT EXISTS`: уникального ограничения нет, `ON CONFLICT` без него невозможен.

## 4. HikariCP простыми словами

- Открыть соединение с PostgreSQL дорого: TCP, аутентификация, запуск backend-процесса на стороне БД.
- Пул открывает соединения заранее и выдаёт их запросам по очереди, после запроса соединение возвращается в пул.
- До стадии 1 используется `DriverManagerDataSource`: каждый запрос открывает и закрывает своё соединение.
- Размер пула задаётся `TUNING_POOL_SIZE` (по умолчанию 10).
- Слишком маленький пул: запросы стоят в очереди за соединением. Слишком большой: Postgres тратит время на переключение между процессами, и `max_connections` не бесконечен (здесь 200).
- Размер выбирается замером: прогоните стадию 1 с несколькими значениями (например 10, 20, 50) и оставьте то, при котором p95/p99 лучше. Результат запишите в таблицу ниже.

Почему пул стоит сразу после baseline: без пула большую часть времени запроса занимает открытие соединения, и выигрыш от индекса на `likes` просто не виден. Пул убирает этот шум, и дальше каждая стадия измеряется честно.

## 5. Как запустить

Требуется Docker (Colima) и standalone `docker-compose`.

```
make init
make up
make stage N=0
make stage N=1
make stage N=2
make stage N=3
make stage N=4
make stage N=5
```

`make bench-all` делает `reset`, `up` и все стадии 0-5 подряд. `make explain N=<стадия>` пишет планы в `benchmark-results/explain/`. `make k6 S=<сценарий> N=<стадия>` запускает один сценарий. `make help` показывает все цели.

Что делает `make stage N=...`: поднимает БД, пересоздаёт приложение с профилем `bench` и нужной стадией, ждёт готовности, снимает EXPLAIN, затем запускает k6-сценарии `smoke`, `mixed`, `hot_post` (на стадии 5 ещё `lag`). Результаты лежат в `benchmark-results/stage<N>-<сценарий>.json` и `.md`.

Порты на хосте: PostgreSQL primary 5442, replica 5443, приложение 8081 (стандартные порты были заняты, значения вынесены в `.env`). Реальный `.env` в `.gitignore`, шаблон — `.env.example`.

Сценарии k6:

- `smoke` — один проход по логике (двойной лайк, дедупликация просмотра, чужой и неизвестный токен);
- `mixed` — 64 VU, 10 с прогрев и 30 с измерения: 70% батч-чтений ленты из 20 постов, 25% цикл просмотра, 5% лайк и unlike;
- `hot_post` — 64 VU, 15 с, все просмотры одного поста;
- `lag` — только стадия 5: сколько проходит от лайка на primary до появления `liked_by_me` при чтении с replica.

В `smoke` специально есть два запроса, которые должны вернуть 400. Поэтому `http_req_failed` в k6 для smoke показывает около 13%: k6 считает любой 4xx ошибкой, хотя здесь это ожидаемое поведение. Проверки `checks` при этом должны быть 100%.

## 7. Что дала каждая стадия

### Стадия 0 → 1: пул

Ожидаемый механизм: на каждый запрос больше не открывается TCP-соединение и backend-процесс Postgres. Этот эффект виден на `hot_post`: RPS вырос с 1013 до 2021, p95 упал с 138.88 до 4.66 мс, p99 с 281.71 до 18.95 мс. Запросы там по одному посту и простые, поэтому цена подключения была заметной долей задержки.

На `mixed` пул ничего не дал: p99 всё равно 35 с, 24.62% запросов завершились ошибкой, всего 99 запросов за прогон. Причина в плане запроса, а не в соединениях: без индекса каждый `COUNT(*)` — это `Parallel Seq Scan` по 20M строк. Фрагмент `EXPLAIN ANALYZE` на стадии 1:

```
Finalize Aggregate (actual time=372.964..379.209)
  ->  Parallel Seq Scan on likes (rows=6.67 loops=3)
        Rows Removed by Filter: 6666660
        Buffers: shared hit=64064 read=63325
Execution Time: 389.369 ms
```

Один запрос читает около 127 тыс. страниц и занимает около 390 мс при 4 CPU и 64 параллельных клиентах. Лишние запросы стоят в очереди, и пул размера 10 только переносит очередь из Postgres в HikariCP. Вывод: пул помогает, когда сам запрос быстрый; без индекса он не спасает. Причину ошибок 24.62% отдельно не разбирали (вероятнее всего таймаут ожидания соединения из пула, но это не проверено). С пулом 20 и 50 доля ошибок была 20.11% и 1.08%, задержки при этом остались десятками секунд (см. выше).

### Стадия 1 → 2: первичный ключ

Механизм подтвердился. `Seq Scan` по 20M строк заменён на `Index Only Scan using likes_pkey`:

```
Стадия 0 (single post): Parallel Seq Scan on likes, Filter post_id = 500
  Rows Removed by Filter: 6666660, ~330 ms
Стадия 2: Index Only Scan using likes_pkey on likes
  Index Cond: (post_id = 500)
Execution Time: 3.911 ms
```

Пакет из 20 постов (`GROUP BY` по `ANY(массив)`): 587.699 мс на стадии 1 → 0.151 мс на стадии 2 (повторный запуск, данные в кэше; первый запуск одиночного запроса 3.9 мс включает чтение с диска). Результат в `mixed`: с 1.8 до 1943.7 RPS, p99 чтения с 48.8 с до 71.2 мс. Это самый большой прирост во всём бенчмарке. `INSERT ... ON CONFLICT DO NOTHING` вместо `NOT EXISTS` убирает гонку baseline (раздел 8), и проверка дубля идёт по индексу.

### Стадия 2 → 3: таблица счётчиков

Механизм подтвердился. Чтение берёт `likes_count` из `post_counters` по PK вместо `GROUP BY` по строкам лайков:

```
Стадия 2: GroupAggregate -> Index Only Scan using likes_pkey (rows=400)
  Execution Time: 0.151 ms
Стадия 3: Index Scan using post_counters_pkey (rows=20)
```

В `EXPLAIN` на прогретых данных разница мала (0.07–0.15 мс на стадии 2 против 0.18 мс на стадии 3: там запрос читает ещё и `liked_by_me`, поэтому сопоставление голыми цифрами EXPLAIN нечестное). Реальный эффект виден под нагрузкой: RPS 1943.7 → 2411.4, p99 всех запросов 68.70 → 49.44 мс, read p99 71.20 → 51.93 мс. Цена — лишний `UPDATE` на каждый лайк, но в смеси лайки составляют 5%, а на `hot_post` разница между стадиями 2 и 3 незначительна (p99 8.96 против 7.48 мс). Эта стадия — лучший результат всего бенчмарка.

### Стадия 3 → 4: партиционирование

`likes` разбита на 8 партиций по `hash(post_id)`. Запрос с равенством по `post_id` направляется в одну партицию (partition pruning), запросы `post_id = ANY(массив из 20 id)` и `liked_by_me` затрагивают все 8.

Ожидание: небольшая разница или небольшое ухудшение. Первый прогон (без `ANALYZE` после миграции) дал сильную деградацию: RPS 2411.4 → 881.4, read p99 51.93 → 170.44 мс, `hot_post` p99 7.48 → 196.82 мс. В плане было видно `rows=12455` при фактических 20 (нет статистики у новых партиций), `Bitmap Heap Scan` вместо индексного доступа и 95.777 мс на пакетный запрос против 0.151 мс на стадии 2. Поэтому в конец миграции V3 добавлен `ANALYZE likes;`, и стадия 4 перепрогнана на сброшенной и заново заполненной БД.

Реальный план после `ANALYZE` (`make explain N=4`):

```
Aggregate
  ->  Bitmap Heap Scan on likes_p3 likes
        (rows=20) (actual rows=20.00)
        Buffers: shared hit=4 read=22 dirtied=20
        ->  Bitmap Index Scan on likes_p3_pkey
              Index Cond: (post_id = 500)
Planning Time: 0.656 ms
Execution Time: 2.548 ms
```

Pruning сработал (только `likes_p3`), оценка стала точной (`rows=20`), время запроса упало с 7.905 до 2.548 мс. Пакетный запрос по 20 постам: `HashAggregate` над `Append` по 8 партициям, время 9.645 мс (было около 72–95 мс; на стадии 2 — 0.151 мс). Проверка `liked_by_me`: `Index Only Scan` по 8 партициям, `Heap Fetches: 0`, 0.148 мс.

Сравнение до и после `ANALYZE` (стадия 4, `mixed`):

| Версия | RPS | read p95, ms | read p99, ms | `hot_post` RPS | `hot_post` p99, ms |
|---|---|---|---|---|---|
| без ANALYZE | 881.4 | 115.36 | 170.44 | 1142.9 | 196.82 |
| с ANALYZE | 1821.4 | 47.56 | 80.78 | 1981.8 | 23.73 |
| стадия 3 (для сравнения) | 2411.4 | 28.70 | 51.93 | 2057.5 | 7.48 |

Вывод: гипотеза об отсутствии статистики подтвердилась частично. `ANALYZE` вернул точные оценки и примерно вдвое улучшил RPS и read p99. Но стадия 4 всё равно хуже стадии 3 (read p99 80.78 против 51.93 мс), и цель 50 мс не достигнута. Остаток разрыва не измерялся. Возможные причины, не проверенные: планировщик для `COUNT(*)` по-прежнему выбирает `Bitmap Heap Scan` с `dirtied=20` (вероятно, нет visibility map, так как после массовой загрузки не было `VACUUM`, а `Index Only Scan` без неё не работает), а запросы по массиву обходят все 8 партиций и увеличивают время планирования. Прогон `VACUUM (ANALYZE) likes` для проверки первой причины не делался. Оговорки: один прогон, БД перед ним сброшена и заполнена заново без нагрузки k6 между стадиями, поэтому состояние кэша и autovacuum могло отличаться от `bench-all`.

### Стадия 4 → 5: read replica

Чтения (`@Transactional(readOnly = true)`) уходят на replica через `AbstractRoutingDataSource` с `LazyConnectionDataSourceProxy`, записи идут на primary. Что показали данные:

- Сравнение ниже идёт со СТАРОЙ стадией 4 (без `ANALYZE`, результаты в `benchmark-results/before-analyze/`); стадия 5 не перепрогонялась. Относительно новой стадии 4 (read p99 80.78, `like` p99 72.91, `view` p99 64.25, `hot_post` p99 23.73 мс, RPS 1821.4) выигрыш меньше, а чтения на replica (read p99 254.03 мс) остаются заметно хуже.

- Изоляция записей сработала: `view` p99 167.86 → 55.84 мс, `like` p99 169.31 → 50.08 мс, `hot_post` p99 196.82 → 10.91 мс (RPS 1142.9 → 2045.3, как на стадии 3).
- Чтения на replica остались медленными: read p99 170.44 → 254.03 мс. Общий RPS не изменился (881.4 → 865.7).
- Лаг реплики мал: p99 13 мс (требование 2 с).

План с replica (`benchmark-results/explain/stage5-replica.txt`): запрос `post_counters` — `Execution Time: 9.966 ms` (холодный кэш реплики), проверка `liked_by_me` — `Append` по всем 8 партициям, около 21 мс на холодных страницах.

Объяснения, не проверенные отдельными экспериментами: (1) replica стартует с холодным кэшем, а `shared_buffers` у primary уже прогрет `BenchSeeder`; (2) на replica идут и WAL replay, и запросы, и всё это на тех же 4 CPU, что у primary, app и k6; (3) `liked_by_me` обходит 8 партиций. Ни одно из трёх не подтверждено измерением. Главный вывод: replica разгружает primary и защищает записи, но на одной ВМ без выделенных ядер для реплики чтения от этого быстрее не становятся.

## 8. Честные ограничения

1. Партиционирование почти не ускоряет точечные запросы: с PK индекс и так находит строку за несколько обращений. Ценность партиций в обслуживании (vacuum, drop старых данных, меньшие индексы), а не в скорости точечного чтения. Запросы по массиву id даже затрагивают все партиции.
2. Реплика отстаёт. Пользователь может поставить лайк и сразу прочитать старое значение. Решение на клиенте — оптимистичное обновление интерфейса после лайка. Здесь оно не реализовано. Лаг измеряет сценарий `lag` (граница задания — 2 с).
3. `view_dedup` растёт без ограничений: старые строки не удаляются. На 50M постов это отдельная проблема.
4. Горячий пост блокирует строку `post_counters`: все `UPDATE` одного поста выстраиваются в очередь на row lock. Это показывает сценарий `hot_post`.
5. Запись счётчика на каждый просмотр нагружает БД. Эти три проблемы (пункты 3-5) решаются в SIS #4: Redis, Kafka и агрегатор, который пишет счётчики пачками.
6. Датасет уменьшен до 1M постов вместо 50M (Colima: 4 CPU, 8 GiB RAM, 60 GiB диск). Абсолютные числа нельзя переносить на боевой объём, важны относительные изменения между стадиями.
7. k6 ходит через REST, поэтому стоимость HTTP и JSON одинакова на всех стадиях. Она входит в измеренные задержки и сжимает видимую разницу между стадиями.
8. В профиле `bench` минимальная длительность просмотра снижена с 2 с до 50 мс (`counter.min-view-duration`). Иначе каждый просмотр держал бы VU 2 секунды, и нагрузка не достигала бы значимых RPS. Это упрощение логики сервиса ради бенчмарка, правило из SIS #1 (2 с) в основном профиле остаётся.
9. Достигнутые RPS далеки от требований (44k чтений/с и около 20k записей/с): лучший результат — 2411 RPS суммарно на стадии 3 в смеси (70% чтений, 25% просмотров, 5% лайков), то есть порядка 1/25 от нужной нагрузки. Один Postgres в Docker на ноутбуке её не достигает; это ожидаемо, и разрыв закрывается горизонтальным масштабированием, которое по условию задания не используется.
10. В baseline проверка `WHERE NOT EXISTS` без уникального ограничения имеет гонку: два параллельных лайка одного пользователя могут оба пройти проверку и создать дубликат, а счётчик увеличится дважды. Со стадии 2 это невозможно благодаря PK и `ON CONFLICT`.
11. Все компоненты (app, primary, replica, k6) работают на одной ВМ с 4 CPU и конкурируют за ядра. Поэтому выигрыш от реплики на стадии 5 не виден: отдельного железа у неё нет.
12. Цель read p99 < 50 мс не достигнута: лучший результат 51.93 мс (стадия 3).
13. Стадии 4 и 5 в `mixed` медленнее стадии 3. Для стадии 4 перепрогон после `ANALYZE` улучшил результат вдвое (RPS 881 → 1821, read p99 170 → 81 мс), но стадии 3 он не достиг; остаток (возможно, нет visibility map, обход 8 партиций) не проверен. Стадия 5 снята на старой V3 без `ANALYZE` и не перепрогонялась; её причины (холодный кэш реплики, общий CPU) остаются гипотезами.
14. Причина 24.62% ошибок на стадии 1 не диагностирована. Размер пула (10/20/50) измерен одним прогоном на значение, только на стадии 1; причина ошибок и их спад с ростом пула не выяснены.
15. RPS в таблице посчитан k6 за весь прогон, включая прогрев, а задержки — только за фазу измерения. k6 предупреждает о более чем 100k уникальных временных рядов (теги URL); на результаты это не влияет, но увеличивает расход памяти k6.

## 9. Настройки PostgreSQL 18 и ресурсы

Образ `postgres:18` для primary и replica, параметры запуска:

| Параметр | Значение | Зачем |
|---|---|---|
| `shared_buffers` | 512MB | кэш страниц Postgres, достаточно для рабочего набора 1M постов |
| `max_connections` | 200 | запас над размером пула |
| `wal_level` | replica | нужен для streaming replication |
| `max_wal_senders` | 10 | процессы, отдающие WAL реплике |
| `hot_standby` | on | replica принимает запросы на чтение |

Replica создаётся `pg_basebackup -R` и подключается к primary по streaming replication. После заполнения данных приложение ждёт, пока replica дойдёт до позиции WAL primary (`ReplicaCatchUp`), и только потом начинается замер.

Colima: 4 CPU, 8 GiB RAM, 60 GiB диск. Версия Spring Boot 4.1.2, Java 21.
